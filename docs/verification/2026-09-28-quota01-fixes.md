## D. Fallback trap — VERIFIED FIXED (2 minor residuals)

The trap was real and was a consequence of making `taskband.enabled` a cross-platform master switch.
Chain: switch OFF → `requested_provider_entries` empty → `plan_menubar([])` → `apply_runtime_entry(app, false)`
→ which called `open_screen(app, "settings")` unconditionally.

The fix gates that recovery:

```rust
fn missing_menu_entry_action(surface_enabled: bool) -> MissingMenuEntryAction {
    if surface_enabled { MissingMenuEntryAction::OpenSettings } else { MissingMenuEntryAction::LeaveWindowAlone }
}
```

**(b) The helper is not vacuous.** The two tests assert *opposite* outputs — `false`→`LeaveWindowAlone`
and `true`→`OpenSettings` — so neither branch is dead code:

```
test menubar::tests::a_disabled_instance_surface_does_not_open_settings ... ok
test menubar::tests::a_lost_menu_bar_still_opens_settings ... ok
```

**(b) The `is_none_or` default preserves prior behaviour.** `try_state::<Arc<SettingsService>>().is_none_or(|s| s.get().taskband.enabled)`
yields `true` when the settings service is absent → `OpenSettings` → the original recovery. Correct
and fail-safe.

**(c) A genuinely lost menu bar still recovers.** `surface_enabled == true` → `OpenSettings`, i.e.
the safety net for creation failure / dragged-out items / reconciliation panic is intact. Not
over-corrected.

**(a) The trap is closed — with two honest residuals.**

*Residual D1 — the tray/entry flag is still reported unavailable.* `apply_runtime_entry` returns
early **before** `set_menu_entry_available(true)` can run, and `set_menu_entry_available(false)`
(desktop_integration.rs:100-105) sets `tray_available=false` **and** forces floating. Consequently
`exits_on_close = is_floating() && !tray_available()` is **true** while the switch is off. Closing
the popup therefore routes to `MainWindowDismissAction::RequestLeaveSettings` rather than a plain
hide, and the user sees a quit-confirmation dialog (`requiresLeaveSettingsConfirmation()` checks
`settingsState?.trayAvailable === false`). This is **recoverable** — the dialog can be cancelled —
but it is a real behavioural surprise: with the menu bar deliberately off, closing the popup
prompts to quit rather than simply hiding.

*Residual D2 — relaunching the app opens Settings, not the popup.* `window.rs:468-472`:
`activate_existing_instance` calls `open_settings_window` when `provider_instance_count() == 0`,
which is exactly the switch-off state (`menubar.rs:974` sets the count to `actual_ids.len()`), and
single-instance reopen goes through `activate_existing_instance`. So a user who turns the menu bar
off, closes the popup, and reopens Quota01 lands in **Settings**, not the popup.

**Can a user be stranded? No — four independent routes back were verified:**

1. **Tauri tray icon** — built unconditionally at `lib.rs:116` with an `open` item that calls
   `show_main_window` (`lib.rs:124-131`). This does **not** depend on `tray_available`. This is the
   primary way back and it always exists on macOS.
2. **Tray `settings` / `customize` items** — `open_screen`, always available.
3. **Global shortcut** — `toggle_main_window` (`lib.rs:296-300`), if the user configured one.
4. **Reopen the app** — single instance → `activate_existing_instance` → Settings (D2), from which
   the tray `open` item reaches the popup.

So D1/D2 degrade the experience but do not trap. **I do not consider the trap a failure**; I report
D1/D2 because the Lead asked for honesty rather than softening, and because D1's quit-prompt is
user-visible.

## E. OPEN DEFECT — unconditional `cancel_pending()` race (low severity)

`schedule_outside_click_dismiss` (window.rs:1509) cancels the dismissal token **without checking
that the token is still current** in the in-app branch:

```rust
let focus_move = classify_popup_focus_move(still_focused, own_app_is_frontmost);
if focus_move == PopupFocusMove::OwnApplicationWindow {
    guard.cancel_pending();     // <-- no is_current(token) guard
    return;
}
if guard.is_current(token) && should_dismiss_popup_on_focus_loss(focus_move) { ... }
```

The `OutsideApplication` branch **does** check `is_current(token)`; the in-app branch does not.
Because `cancel_pending()` bumps a shared generation counter (`popup.rs:14-16`), a **stale**
callback can invalidate a **live** token belonging to a newer dismissal:

```
stale_token=0 current_token=1
after stale in-app callback: is_current(current_token) = false
VERDICT: live dismissal token 1 was SILENTLY INVALIDATED -> popup will NOT auto-dismiss
```

(Executable reproduction `/tmp/vx-check/race-proof.rs`, using the real guard semantics.)

**Impact:** narrow. It requires a dismissal callback to fire late *and* the focus loss to be an
in-app move, in the same 100 ms window as a newer show. The observable effect is that the popup
occasionally fails to auto-dismiss on one click — a minor annoyance, never a crash or a stuck
window. The `OutsideApplication` path (the common desktop-click case) is correctly guarded.

**Not covered by tests.** The two token tests exercise the pure helper
(`classify_popup_focus_move`), not the guard interaction in the runtime closure; nothing asserts
that a stale in-app callback leaves a newer token intact. Suggested (for the owner, not applied):
guard the in-app branch with `if guard.is_current(token) { guard.cancel_pending(); }`, and add a
test asserting a stale in-app callback does not consume a newer token.

### Defect E — stale token race in `schedule_outside_click_dismiss` — FIXED

## Lead addendum 2 — popup/coexistence semantics REVERSED (user-reported regression)

The coexistence fix above was over-corrected. The user reported: *"打开设置界面后 popup 应该自动隐藏；
现在点击设置界面的时候 popup 依然在，会挡住设置界面"* — i.e. after opening Settings the popup stayed
on screen and covered it, and clicking anywhere outside the popup failed to dismiss it.

### What was wrong

The original change removed BOTH directions of mutual exclusion and then judged focus loss at the
**application** level (`NSApplication::isActive()`), so a click that merely moved focus into Quota01's
own Settings window was treated as "still ours, keep the popup". That is the opposite of what a
transient menu-bar panel should do: the popup is anchored under the menu-bar item while Settings is
centred, so keeping it up covers the very window the user just clicked into.

### Corrected semantics (asymmetric on purpose)

| Event | Behaviour |
|---|---|
| Click the menu-bar/tray item (reveal popup) | Popup shows; **Settings untouched** |
| Open Settings | Popup is **hidden** |
| Click anywhere outside the popup — desktop, another app, **or our own Settings window** | Popup is **hidden** |
| Popup still has keyboard focus | Nothing happens |

The two directions are deliberately not symmetric: revealing the popup must never discard Settings
work, but a click outside the popup always dismisses the panel.

### Code changes

- `opening_settings_keeps_popup_visible()` → `opening_settings_hides_popup()`; `open_settings_window`
  now hides a visible popup before showing Settings.
- `classify_popup_focus_move(still_focused, own_app_is_frontmost)` →
  `classify_popup_focus_move(still_focused)`. `PopupFocusMove` is now `StillFocused | OutsidePopup`;
  the `OwnApplicationWindow` variant is gone, so there is no longer any path that keeps the popup up
  for an in-app click.
- Deleted the now-unused `own_application_is_frontmost()` helper.
- `schedule_outside_click_dismiss` keeps the `is_current(token)` stale-callback guard added in
  addendum 1 (still needed so a late callback cannot hide a freshly reopened popup).

### Tests (840 Rust total; this cluster rewritten)

`opening_settings_hides_the_popup`, `a_focus_move_into_the_settings_window_dismisses_the_popup` (the
reported bug), `a_focus_move_to_another_application_dismisses_the_popup`,
`a_still_focused_popup_is_never_dismissed`, `an_outside_click_still_honours_the_pending_dismissal_token`,
`a_stale_callback_leaves_a_newer_token_intact`.

`revealing_the_popup_never_hides_the_settings_window` is **kept** — that direction is still required.
